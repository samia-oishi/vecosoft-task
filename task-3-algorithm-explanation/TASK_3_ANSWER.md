I used a JavaScript `Map` to store the cache keys and values because it provides average O(1) lookup, insertion, and deletion while preserving insertion order. The first entry represents the least recently used item and the last entry represents the most recently used item. On a successful `get`, I remove and reinsert the key so it becomes most recently used. On `put`, an existing key is updated and refreshed; if capacity is exceeded, the oldest entry is removed.

Both `get` and `put` are average O(1), and the cache uses O(capacity) space because it stores no more than the configured number of entries. A poor access pattern would be reading hundreds of unique records sequentially with a cache capacity of two. Each new record would evict an older record before reuse, producing a very high miss rate. AI helped me check duplicate-key behavior and eviction order. I kept the suggestion that updated keys become most recently used, but rejected adding a second data structure because JavaScript `Map` already provides the ordering needed for this compact implementation.
